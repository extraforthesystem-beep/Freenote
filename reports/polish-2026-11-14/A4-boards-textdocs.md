## Board canvas and culling — the earlier claims, checked

**Canvas size.** Fixed, and decided by a constant, not by content. `BoardEditorView.swift:23` is `static let worldSize = CGSize(width: 50_000, height: 50_000)`, and it is handed straight to the canvas at line 194 (`pageSize: Self.worldSize`). Stroke coordinates are shifted by `static let worldOffset = CGPoint(x: 25_000, y: 25_000)` (line 26) so an old board's origin lands in the middle, and shifted back on save (606-608, 736-793). Free zoom is a fixed range, `0.1...4.0` (line 28), and the canvas's scroll size is `pageSize × zoom` (`PencilCanvasView.swift:676-679`, `InkCanvasView.syncFreeContentSize`). The only content-derived size is Zoom to Fit, which zooms the scroll view to `board.bounds()` inset by 48 (line 485-489) — it moves the camera, it does not change the world. So: **yes, fixed-size canvas, 50,000 × 50,000, independent of what the board holds.** Consequence: at 10 % zoom the visible world is ~10,000 pt wide, so `items(in: viewport)` would still be the only sane way to decide what to draw; and the whole board is always inside the world, so nothing is ever unreachable.

**Are off-screen items still built as views?** Two answers, and they differ:

- iPad item layer: **culled, but not skipped.** `BoardItemLayer` tests `if let frame = item.frame, frame.intersects(visible)` (BoardCanvasChrome.swift:102) before building `BoardItemView`, so an off-screen item gets no view body, no image decode and no layout. But `ForEach(items)` (line 101) still runs its closure once per item on every viewport update, and `items` is `board.normalizedZOrder().filter { $0.frame != nil }` (BoardEditorView.swift:185) — a sort of every item — recomputed whenever the board changes (every drag frame), not when the viewport changes. So the earlier audit's claim is **wrong for the iPad item layer's drawing** and **right about the iteration cost** (A4-11).
- Mac preview and every board thumbnail: **not culled at all.** `BoardStaticItemLayer` (BoardItemViews.swift:221-252) is `ForEach(items)` with no bounds test at line 230, and it is used by `macCanvas` (BoardEditorView.swift:335, `items: board.normalizedZOrder()`) and by `BoardThumbnail` (BoardThumbnail.swift:56). Every item — including full-resolution image decodes — is built for a 52 pt square or a scaled preview (A4-14).
- Ink: the app does no ink culling. The strokes go to PencilKit's own canvas (`pageSize: Self.worldSize`), so how much of the 50,000 pt world is rasterised is PencilKit's business, not this code's.

**Does `Board.items(in:)` exist, and who calls it?** It exists — `Board.swift:157`, `public func items(in rect: CGRect) -> [BoardItem]`, implemented as `normalizedZOrder()` then a bounds-intersect pass then a connector fix-up (158-171). **Nothing calls it.** A repo-wide search for `items(in` finds only its definition and an unrelated `PageTemplateCatalog.items(in category:)`; the board rebuilds the same test inline at BoardCanvasChrome.swift:102 and again at BoardEditorView.swift:829 for hit-testing. Worth noting before anyone adopts it: it calls `normalizedZOrder()` on every call, so dropping it into the body would re-sort the board once per frame instead of once per board change. The right shape is a cached sorted array on `Board` state (recomputed when the board changes) and a visible slice computed per viewport change in the parent, not a sort inside a body.

**Frame cost as a board grows to 500 items.** Per finger-drag frame, on the main actor:

1. `board.setFrame` mutates the `@State` board, so `canvasArea` re-evaluates: `board.normalizedZOrder()` (Board.swift:136-142 — a `deletedItemIDs` filter plus a sort of 500 with a UUID-string tiebreak) and `.filter { $0.frame != nil }` (another 500-element pass).
2. `BoardItemLayer.body` runs: 500 `ForEach` elements and 500 `frame.intersects` tests (A4-11).
3. `dragChanged` builds snap targets from all 500 items and does ~18,000 comparisons, twice — x and y (A4-02).
4. `scheduleSave` copies the whole board: `translated` maps 500 items and, for the ink item, allocates a new 6-element transform array per stroke (A4-01).
5. `PencilCanvasView.updateUIView` → `Coordinator.apply`: `strokes.map(\.id)`, `current.map(\.id)` and `allSatisfy { RecordSignature($0) }` over every stroke, each signature copying the transform array (`PencilCanvasView.swift:765-773`).
6. A new `Task`, plus `isSaving` written.

Nothing here is O(visible): steps 1, 3, 4 and 5 are all O(items) or O(strokes). At 500 items this is a per-frame allocation storm on a 60 Hz device. Ink-only drawing (no object drag) avoids 2, 3 and 4 but still pays 1 and 5 per finished stroke.

Panning and pinching are the good path: the `viewport` object's `zoom`/`visibleRect` are read only by `BoardItemLayer`, `BoardDotGrid` and `BoardZoomPill` (BoardCanvasChrome.swift:48-49, 97-98, 504), not by `canvasArea`, so a scroll frame does not re-sort items or rebuild menus — it rebuilds 500 `ForEach` elements (A4-11) and re-draws ~2,400 grid dots per frame (BoardCanvasChrome.swift:50-73, stride 48 doubled until 18 screen pt, so about 57 × 43 dots at 1024 × 768).

## Not checked

- **Actual frame timings.** Everything above is a code-path argument, not a measurement; I ran no builds and no Instruments (both forbidden here). The board's per-frame cost at 500 items should be confirmed with the PERFORMANCE-NOTES §1 template on a board with 500 objects and 2,000 strokes.
- **Whether SwiftUI actually re-runs `BoardItemView.body` per viewport update** (A4-04, A4-12). It follows from `BoardItemLayer.body` reading `viewport.zoom`/`visibleRect` and rebuilding its children, but I could not run the app to confirm the SwiftUI instrument shows those bodies.
- **`PencilCanvasView`'s full behaviour.** I read the `updateUIView`/`apply`/viewport-reporting paths the board depends on, not the whole file (1,000+ lines: gestures, hold-to-shape, eraser filter). Any per-frame cost inside it outside those paths is not reported.
- **Mac-only code paths** (`macCanvas`, `macInkImage`) were read but not run; A4-03's severity assumes a board big enough for the render to be visible.
- **Haptics and pointer** were out of scope per the brief, and nothing in these files uses them.
- **BoardKit's `BoardLayout.swift`, `BoardCamera.swift`, `BoardMerge.swift`** were read for context; no app file in my area misuses them, so they produced no findings.
- **Dynamic Type at large sizes in the board's in-place editor** (BoardCanvasChrome.swift:421-432): the frame is clipped to the item's height at the current zoom, so very large text would be cut off — but the fonts are fixed, so the case cannot currently arise. Not reported as a finding.

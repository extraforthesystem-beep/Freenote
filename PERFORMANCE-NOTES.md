# Performance notes — base iPad pass

Written 2026-11-12. Target: base iPad (A-series, 4 GB RAM, 60 Hz, so a 16.7 ms frame).

All numbers below were measured on an **M1 Max Mac**, in **release** builds (`swift test -c release -Xswiftc -enable-testing`), unless they are marked otherwise. Before/after pairs are medians of 5 runs. Expect a base iPad to be roughly 2–3× slower. The benchmarks are off by default, so the suites stay fast:

```
cd Packages/InkKit    && NOTEAPP_BENCH=1 swift test -c release -Xswiftc -enable-testing --filter RenderBenchmarks
NOTEAPP_BENCH_PDF=/path/to/big.pdf  (adds the real-PDF benchmark to the line above)
cd Packages/SearchKit && NOTEAPP_BENCH=1 swift test --filter firstIndexPass
```

## Fixed

| # | Hot path | Evidence | Fix | Before → after |
|---|---|---|---|---|
| 1 | **Search index first pass** (`SearchIndex.update`) | The whole JSON index was re-encoded and rewritten after **every page**, so a pass cost O(N²). | Indexing passes defer writes and flush every 25 pages (`beginDeferringWrites` / `flushDeferredWrites` / `endDeferringWrites`). `load()` flushes first, so no change is lost. An index that `reset()` replaced is never written back. | 600 pages with ~2 KB of text each: **5.48 s → 0.31 s** (debug) |
| 2 | **Ink round trip, PencilKit reads** (`PencilCanvasView.Coordinator`, `HoldToShape`) | `canvas.drawing.strokes` bridges every stroke out of PencilKit: **2.1 ms at 2,000 strokes**. One stroke read it 4 times: at touch-down (hold observer), twice in `reportDrawingChange`, and once in `apply`. | Read it once per change. Everywhere else uses `baselineStrokes`, which every path that changes the drawing already keeps current. | 4 reads → 1 per stroke: **~8.4 ms → ~2.1 ms** at 2,000 strokes |
| 3 | **Ink round trip, merge** (`StrokeOrder.merge`/`renderOrder`) | Every finished stroke re-sorted the whole page, which is almost always already in order, and copied every record into a dictionary. | One pass checks whether the page is already in order (the sort is stable, so it then returns its input). The dictionary maps ids to indices instead of records. | **2.86 → 0.98 ms** at 2,000 strokes |
| 4 | **Ink round trip, converter** (`IncrementalStrokeConverter`) | Rebuilt its whole cache dictionary for every stroke. | Updates it in place and prunes only when strokes were removed. | **5.11 → 4.59 ms** at 2,000 strokes |
| 5 | **Whole editor re-rendered per stroke** (`NotebookPane`) | The banners (`layerBlock`), the 18 `.disabled(session.page == nil)` menu items and the bookmarks menu read `session.page`, which changes with every stroke. That re-ran the pane's body: the toolbar, both menus and about 30 modifiers. | `NotebookSession` derives `currentPageID` and `activeLayer` in `didSet` and assigns them only when they change; the chrome reads those. I checked that an `@Observable` `didSet` with a guarded assignment does not notify. | The pane body no longer depends on `page`. Only the page content (canvas, paper, elements) updates per stroke. Not timed: needs Instruments (see below). |
| 6 | **Manifest reload after every save** (`reloadManifest`) | Each debounced save (400 ms after the last stroke) replaced `manifest`, whose `updatedAt` always changes. That re-rendered the toolbar, thumbnail strip cells, page pill and page scroller. | Skip the assignment when only `updatedAt` changed. Nothing reads the session's `updatedAt`; the library reads its own copy from disk. | One fewer full chrome re-render per save |
| 7 | **Page activation stall on PDF/photo pages** (`PaperBackground`) | An uncached 2× paper is drawn **synchronously on the main actor** when a page becomes active: **77 ms per page** for a scanned PDF (421-page book), **11 ms** for a text PDF (1,058 pages). | `PagesView.render` pre-renders the 2× paper for nearby pages with a PDF page or image, off-main at utility priority, and stores it in `PageBackgroundCache`. Template-only pages keep the cheap synchronous path. `Page.withoutTape` is shared so the cache keys match. | Activating a page you scrolled to hits the cache instead of a 77 ms main-thread draw |
| 8 | **Thumbnail strip, fling** (`PageThumbnailCell`) | It rendered in `Task.detached`, which **does not inherit** the cell's `.task` cancellation. A fling over a scanned PDF still decoded a full-page scan for every cell it passed (63 ms each at thumbnail scale). | Cancellation is forwarded with `withTaskCancellationHandler`, and the render checks it before it starts. | Off-screen cells waiting for a thread no longer render |
| 9 | **Memory warnings** | Five `NSCache` image caches: page images 128 MB, paper 128 MB, thumbnails 64 MB, templates 64 MB, covers 48 MB, so **432 MB** at their limits. `NSCache` is not documented to evict at a memory warning. | `MemoryPressure` empties all five on `UIApplication.didReceiveMemoryWarningNotification`. Everything re-renders on demand; covers come back from their disk cache. | Deterministic purge |
| 10 | **Launch work on main** (`LibraryCovers.pruneStaleCovers`) | Lists and stats every cached cover file. It ran in a `Task` that inherited the main actor during `AppModel.start`. | `nonisolated`, run in `Task.detached(priority: .utility)`. | Off the main actor |

## Checked and dismissed

- **Caching parsed PDFs (candidate 4).** Measured: `PDFDocument(url:)` plus `page(at:)` plus `annotations` costs **0.2 ms** (synthetic 400 pages), **0.6 ms** (real 421 pages) and **1.1 ms** (real 1,058 pages) per call. Drawing the page costs **5 ms, 63 ms and 10 ms** respectively. Opening the file is 1–2 % of a render. A shared `PDFDocument` would also need a lock, because PDFKit does not document it as thread-safe, and that lock would serialise the concurrent thumbnail renders. Not worth it. The same applies to `SearchIndex.pdfText`, which runs on the index actor.
- **Image elements decoded per render.** Every render decodes the image again, but renders are themselves cached (page images, paper, thumbnails, covers), and the costly case is now pre-rendered (fix 7). A decoded-image cache would hold full-resolution bitmaps (48 MB for a 12 MP photo) on a 4 GB device. Left as is.
- **Page file rewritten per stroke.** No: saves are debounced 400 ms and coalesced (`scheduleSave`), and run in order on the `LibraryStore` actor, off the main actor. A save does encode the whole page: **0.83 s for 2,000 strokes × 64 points**, off main. That is the cost of the JSON format, so it is not fixable without a format change. It is listed under "Instruments" for a real-device number.
- **Inactive-page renders (seamless scroll).** They are off-main (`Task.detached(.userInitiated)`), one at a time, rebuilt from the slots near the viewport on each update, and skipped when the slot is gone. The scale is quantised to half steps and capped at 3×. Slots exist only for the viewport plus half a screen on each side. One `UIHostingController` lives per notebook and scroll direction (`.id`); the active page moves its view between slots and never recreates it.
- **Zoom View.** The second canvas decodes only the echoed stroke (`rebuiltStrokes` reuses live strokes). Its paper uses the same cached `PaperBackground` at a bucketed scale with a 150 ms debounce. A band move changes only the canvas viewport. Its cost is a second PencilKit canvas, which needs a device measurement (below).
- **Version history.** Snapshots are written at most once per page per 120 s, encoded and pruned in a detached utility task on the history actor. Launch pruning runs on that actor too.
- **Search indexing on the main actor.** `HandwritingSearch` is `@MainActor`, but every step awaits `LibraryStore` or the `SearchIndex` actor; only the loop bookkeeping runs on main.
- **Haptics / timers.** `UICanvasFeedbackGenerator` is created once per canvas and reused. The audio elapsed timer (500 ms) is cancelled on stop.
- **Tool-state save debounce (600 ms), thumbnail edit debounce (1.5 s), ink save debounce (400 ms).** Left as is.

## Known remaining costs (not changed)

- **Recording re-renders the pane at 2 Hz.** `NotebookPane` reads `session.audio.elapsed` for the toolbar's recording label. Fixing it means moving that label into its own view inside `EditorToolbar`, a toolbar API change I left for a UI pass.
- **`StrokeSignature` at 2,000 strokes: about 2.8 ms**, of which `stroke.mask` bridging is 1.0 ms. This is what lets the converter recognise unchanged strokes. PencilKit gives no cheaper identity check.
- **Page JSON encode, 0.83 s for a 2,000-stroke page** (off main). If it shows up as save lag on a device, a binary stroke payload is the fix. That is a format change.

## Needs Instruments on a real base iPad

Use a Release build on the device, with a notebook made for each test: (a) a **2,000-stroke handwritten page**; (b) an **imported 400-page scanned PDF**.

1. **Per-stroke main-thread cost.** Template: **Time Profiler** with **Hangs** and **SwiftUI** instruments. Record 30 s of fast handwriting on page (a). Look at the main thread around each stroke end: `canvasViewDrawingDidChange` → `strokesChanged` → the SwiftUI update → `PencilCanvasView.updateUIView`. **Bad: more than 8 ms per stroke end**, which leaves under half a frame for PencilKit, or any hang over 100 ms. In the SwiftUI instrument, confirm that `NotebookPane.body` does **not** run per stroke while `pageContent` does. If the pane's body still shows up, look for a remaining `session.page` read.
2. **Ink latency while saving.** Same recording. Check that the `LibraryStore` actor's `savePage` (JSON encode) never lands on the main thread, and see how long it takes on the device. **Bad: a save over 1.5 s.** Saves queue behind each other, and a notebook closed during one waits for it.
3. **Seamless scroll on the PDF.** Template: **Animation Hitches**. Fling through 50 pages of (b), then let it settle on a page and start writing. **Bad: hitch ratio above 5 ms/s while scrolling, or one hitch over 33 ms when a page activates.** If activation still hitches, check whether `PaperBackground` → `PageBackgroundCache.image(for:)` still renders synchronously (the pre-render missed). Its cache key must match `Page.withoutTape` on both paths.
4. **Memory.** Template: **Allocations** plus **VM Tracker**, or Xcode's memory gauge. Open (b), scroll the whole PDF, zoom to 3× on a few pages, open the thumbnail strip, then go back to the library. **Bad: footprint above 1.2 GB, or memory that does not return to near baseline after closing the notebook.** Then use *Debug → Simulate Memory Warning* in the Simulator, or trigger pressure on the device: dirty memory should drop by the cache sizes (up to 432 MB).
5. **Zoom View.** Time Profiler and Allocations with Zoom View open on page (a). Write 20 strokes in the panel. **Bad: more than 12 ms main-thread per stroke**, since two canvases apply each stroke, or more than 150 MB extra for the second canvas's tiles at high magnification.
6. **Launch.** Template: **App Launch**, with a library of 50+ notebooks and a 1,000-page search index. **Bad: more than 400 ms to first frame**, or main-thread I/O in the first 2 s. Watch `AppModel.start`, `scanNotebooks`, the cover loads and the index `load()`.
7. **First search index pass.** Import (b) with handwriting search on. In Time Profiler, the `SearchIndex` actor should show `write()` about every 25 pages, not after every page.
